# NetTrader: миграция торгового движка на LEAN (крипто + акции)

## Контекст

Диагностика текущего NetTrader (Binance-only crypto futures bot) выявила структурные причины устойчиво отрицательного результата:
- комиссии/funding нигде не вычитаются из PnL и win/loss статистики (`TradeRepository.GetPnlStatsAsync` — только знак `LastKnownPnL`, плюс отдельный баг: `EmergencyStopped` включён в знаменатель, но исключён из `winStatuses` → эмерджи-стоп с плюсовым PnL молча засчитывается как убыток);
- минимальный R:R нигде не проверяется кодом (только пожелание в промпте Gemini);
- размер позиции фиксирован (20% от balance×leverage), не зависит от уверенности сигнала — Kelly не считается;
- лимит "1 позиция на группу корреляции" — только в промпте, не в валидаторе;
- нет проверки margin ratio / расстояния до ликвидации;
- расхождение документации и кода по порогам ML (`CLAUDE.md` устарел: код `MLSignalService.Decide()` использует `minRequiredConfidence=0.60` + динамический гэп 0.02–0.10, а не `MinGap=0.02/Threshold=0.42` из доков).

Пользователь отклонил цель "10%/мес" как недостижимую легальными методами (≈213% годовых) и утвердил:
- **целевая доходность: 10–25% годовых при управляемом риске** (просадки 15–30% — норма для такого профиля, не красный флаг);
- **архитектурное решение: заменить самописный движок на открытый мультиактивный (QuantConnect LEAN)**, чтобы одновременно получить и крипту, и акции, а не чинить риск-слой в изоляции.

Дополнительно пользователь уточнил: новый репозиторий `nettrader-lean` (создан с нуля, greenfield, не форк `nettrader`) —
**сейчас нужен только для одного пользователя** (личная торговля, один набор ключей биржи/брокера). Мульти-юзер
(как в старом `nettrader` — JWT auth, Stripe, BYOK на пользователя) **может понадобиться позже, но не сейчас** —
значит: не строим Api/Auth/Orchestrator/Stripe-слой заранее «на будущее», не тащим их в репозиторий, чтобы не
захламлять его недостроенным кодом. Единственное, что нужно держать в уме, чтобы не закрыть себе дверь: не
хардкодить ключи/конфиг в код алгоритма (уже так — конфиг через `TradingOptions`), и не завязывать `Algorithm/`
на понятие "пользователь" — он и так ничего о пользователях не знает, это просто LEAN-алгоритм с одним портфелем.

Ниже — план этой миграции.

## Почему LEAN, а не альтернатива

LEAN (Apache-2.0, самохостится в Docker) — предпочтительный выбор именно потому, что:
- **тот же язык/рантайм**: алгоритмы LEAN — обычные C# class library, `NetTrader.Domain` (Entities, `SymbolConfig` с группами корреляции, `TradingOptions`) подключается напрямую без моста; существующие ML.NET модели (`ModelLong.zip`/`ModelShort.zip`) грузятся в LEAN-алгоритм без переобучения — это просто NuGet-пакет `PredictionEngine`/`PredictionEnginePool`;
- лицензия допускает коммерческий SaaS (у проекта уже есть Stripe-биллинг);
- Algorithm Framework (Alpha / PortfolioConstruction / RiskManagement / Execution модели) почти один-в-один ложится на нужное разделение "сигнал / размер позиции / риск-правила / исполнение" — именно то разделение, которого сейчас нет (`GeminiAdvisor` сейчас одним вызовом решает и направление, и размер, и SL/TP).

Альтернатива Nautilus Trader (Rust/Python-ядро) отклонена: пришлось бы либо переобучать ML-модели на Python, либо городить gRPC/Redis-мост между .NET-инференсом и Python-стратегией — лишняя латентность и точка отказа без выигрыша для соло/малой .NET-команды.

**Честно про главный риск миграции**: NetTrader — мультитенантный BYOK-сервис (у каждого пользователя свои ключи биржи), а LEAN нативно рассчитан на модель "один алгоритм = одно брокерское подключение = один портфель". Даже QuantConnect Cloud решает мультитенантность через один контейнер на пользователя. Это меняет топологию деплоя: было "один API-контейнер на всех", станет "один API/оркестратор + один LEAN-контейнер на каждого активного live-пользователя". Это отдельный, некоммерческий кусок инфраструктурной работы, не мат-модель — закладываем его отдельным под-этапом в Фазе 2, не размываем.

## Целевая архитектура (актуализировано под single-user-now)

**Из старого `nettrader` не переносится вообще (не сейчас):** `NetTrader.Api` (Auth, JWT, `RefreshTokenStore`, CORS), контроллеры, `TradingHub`/SignalR, Postgres-схема auth/users/payments, Stripe, фронтенд. Для одного пользователя это всё избыточно — данные бэктеста/paper/live можно смотреть через сам LEAN (его отчёты/статистику) или простой личный monitoring (напр. Telegram-уведомления), без веб-API и БД пользователей. Если/когда понадобится мульти-юзер — эти компоненты старого `nettrader` (уже рабочие: JWT auth, шифрование BYOK-ключей, Stripe) переносятся как референс, а не пишутся с нуля.

**В `nettrader-lean` есть/добавляется:** только `Algorithm/` (LEAN-алгоритм, уже создан в репозитории) — `MultiAssetAlgorithm`, `Alpha/MlSignalAlphaModel`, `PortfolioConstruction/FractionalKellyPortfolioConstructionModel`, `RiskManagement/*`, `Common/SymbolConfig`+`TradingOptions`. Один портфель, один набор ключей биржи/брокера в конфиге (не в БД, не per-user).

**Из старого `nettrader` порт нужен только для торговой логики (не инфраструктуры):** `GridTradingManager.cs` (→ заменяется циклом LEAN Algorithm Framework), `GridMathCalculator.cs` (ATR/volume-profile SL/TP переносится в Alpha-модель), `IndicatorEnrichmentService.cs` (→ нативные индикаторы LEAN), `MLSignalService.cs` (30-фичевый вектор + `.zip`-модели — переносится точно, см. ниже), `BinanceFuturesClient.cs`/`BybitClient.cs` (→ брокерские плагины LEAN), `GridSettingsValidator`/`GridSettingsListValidator` (R:R и лимиты корреляции — уже реализованы в `RiskManagementModel` в новом репо).

**Отложено (не строим, пока реально не нужен мульти-юзер):** `NetTrader.Lean.Orchestrator`, per-tenant BYOK, любой Api/Auth/Stripe-слой — см. Фазу 2b ниже.

## ML и Gemini внутри LEAN

- **`MlSignalAlphaModel`** (новый `AlphaModel`): держит индикаторы LEAN на нужных таймфреймах, строит тот же 30-фичевый вектор, что и сейчас `MLSignalService`, гоняет существующие `.zip`-модели без переобучения (крипто, Фаза 0–2), считает ATR-based SL/TP (портируя `CalculateDynamicSlTpByVolumeProfile`, но **исправляя** несоответствие меткам обучения — сейчас fallback 2%/1.5% не совпадает с тренированным барьером +3%/-2%), из этого получает `R`, применяет гейт входа и эмитит `Insight` с `R`/SL/TP в `Insight.Tag` (у LEAN Insight нет нативных полей SL/TP — Tag это идиоматичный носитель).
- **Роль Gemini сжимается**: было — `AnalyzeAndSelectGridsAsync` возвращает готовый размер+SL+TP (то есть Gemini de facto был риск-слоем, что и было одной из причин проблемы). Станет — советующий вход по режиму рынка (`MacroRegimeRiskManagementModel` или множитель уверенности), контракт `{riskMultiplier: 0..1, perSymbolVeto: [...]}` на основе `MacroAnalyzer` (FGI/BTC.D/FOMC) + качественного вывода Gemini. **Gemini больше не задаёт размер позиции и SL/TP.**

## Риск-слой как компоненты LEAN (математика из диагностики)

- **`FractionalKellyPortfolioConstructionModel`** (кастомный, не встроенный `InsightWeightingPortfolioConstructionModel` — тот не знает про асимметричный Kelly и `R` на сигнал): `f = p − (1−p)/R`, клип на `[0, fCap]`, множитель `KellyFraction` (по умолчанию 0.5 = half-Kelly), масштаб по свободной марже и `MaxMarginUsagePercent`.
- **Гейт входа**: `p_model ≥ p_breakeven(R) + запас`, где `p_breakeven = 1/(1+R)` — считается в Alpha-модели вместе с `R`.
- **Минимальный R:R** — жёсткий пол (напр. `MinRewardRiskRatio = 1.5`), независим от `p`.
- **Лимиты по группам корреляции** — новый `CorrelationGroupExposureRiskManagementModel`, использует существующий `SymbolConfig` (переиспользуется как есть, без дублирования).
- **Комиссии/funding** — встроенные `BinanceFeeModel`/`BinanceFuturesFeeModel`/`AlpacaFeeModel` решают проблему "комиссия нигде не вычитается" на уровне движка бесплатно; funding для перпетуалов — проверить, есть ли нативно в текущей версии брокерской модели LEAN, если нет — добавить `Schedule.On` каждые 8ч.
- **Просадка/margin ratio** — встроенный `MaximumDrawdownPercentPortfolio` как база + кастомная проверка под `DailyDrawdownPausePercent`/`EmergencyStopBalancePercent`/`MaxOpenPositions` (эти опции из `TradingOptions.cs` переиспользуются как конфиг) + новый кастомный `RiskManagementModel` на `TotalMarginUsed`/`TotalPortfolioValue` для дистанции до ликвидации — этого не было вообще, пишется с нуля.

## Акции

Брокер — **Alpaca** (комиссия 0%, зрелая интеграция в LEAN, простой paper-trading, ключ+секрет — та же модель BYOK, что уже есть для Binance). IB — опция позже, если понадобятся инструменты вне Alpaca.
**Важно**: текущие ML-модели обучены на крипто-специфичной метке (+3%/-2% за 12ч, 24/7-рынок) — **не переиспользовать для акций**. Для старта Фазы 3 — простая rules-based `EquitiesAlphaModel` на нативных индикаторах LEAN (без ML), честно без псевдо-точности необученной модели; отдельная ML-модель на акции — отдельное решение позже, когда будет история для валидации.

## Данные

- **Крипто**: исторические klines Binance через LEAN ToolBox/community data-source — бесплатно, этого достаточно для 7 whitelisted символов.
- **Акции**: платная подписка QuantConnect — самый надёжный вариант (point-in-time сплиты/дивиденды), либо бесплатно через Alpaca historical bars/Stooq/Yahoo — но с оговоркой: бесплатные данные годятся, чтобы нащупать форму стратегии, не как финальный гейт перед реальным капиталом (нужна ре-валидация на точных данных перед увеличением размера позиции).

## Фазы и критерии перехода

**Фаза 0 — LEAN в Docker, только бэктест, без влияния на пользователей.**
Поднять LEAN-сервис в compose, зафиксировать версию/коммит. Создать `NetTrader.Lean.Algorithm`, портировать индикаторы (сверить пару исторических баров старый-код vs LEAN-нативный на предмет расхождений формул). Собрать `MlSignalAlphaModel` на встроенной `InsightWeightingPortfolioConstructionModel` (ещё не Kelly) — только чтобы проверить генерацию Insight.
*Гейт:* бэктест ≥1 год по 7 символам проходит чисто, распределение направления сигналов примерно совпадает с историческими логами текущего `Decide()`, индикаторы не разъезжаются.

**Фаза 1 — Paper-trading крипты через LEAN + ML, параллельно с текущим live-ботом.**
Добавить реальную `FractionalKellyPortfolioConstructionModel`, гейт входа, `CorrelationGroupExposureRiskManagementModel`, риск по просадке/марже. Paper-trading на Binance testnet, только house-аккаунт (без мультитенантности).
*Гейт:* ≥50–100 закрытых сделок, walk-forward Sharpe/Sortino выше заданного порога **на out-of-sample окне** (не на том, где подбирались Kelly-fraction/гейт), просадка в пределах 15–30%, комиссии/проскальзывание в paper совпадают с бэктест-прогнозом.

**Фаза 2 — Перевод крипты на live LEAN на личном капитале.**
Один LEAN-деплой, один набор ключей биржи (из конфига, не из БД). Старый `nettrader`-путь (`GridTradingManager`, `GridMathCalculator`, `BinanceFuturesClient`, старые валидаторы, `TradingBotWorker`) в новом репозитории и так отсутствует — ничего дополнительно демонтировать не нужно, разве что решить, что делать со старым `nettrader` репо (выключить бот там, оставить как архив/референс для порта логики).
*Гейт:* live-результаты совпадают с paper в пределах ожидаемого шума.

**Фаза 2b — Мульти-юзер (ТОЛЬКО когда реально понадобится, не строить заранее).**
`NetTrader.Lean.Orchestrator` (по одному LEAN-деплою на тенанта с его BYOK-ключами) + Api/Auth/Stripe-слой — переносится как референс из старого `nettrader` (JWT auth, шифрование ключей, Stripe уже рабочие там), не пишется с нуля. Пока не запрошено явно — не создавать эти файлы/проекты в `nettrader-lean`, чтобы не захламлять репозиторий недостроенным/неиспользуемым кодом.
*Гейт (когда актуально):* оркестратор переживает как минимум одну учебную рестарт/креш-рекавери на тестовом тенанте до перевода реальных пользователей.

**Фаза 3 — Акции через Alpaca.**
`EquitiesAlphaModel` (rules-based, без переиспользования крипто-модели). Paper-trading отдельно, свои критерии Sharpe/просадки.
*Гейт:* акции проходят свой walk-forward гейт независимо от крипто-цифр.

**Фаза 4 — (входит в Фазу 2b, если/когда нужен мульти-юзер) Перепривязка `SignalRBroadcastService` и контроллеров к состоянию LEAN** вместо прямых вызовов биржи. Не актуально для single-user сценария — личный мониторинг решается проще (LEAN-статистика, Telegram-уведомления), без веб-фронтенда.
*Гейт (когда актуально):* поведение для фронтенда не меняется (те же формы данных, та же задержка) — полный регресс-прогон контрактов.

## Проверка на каждом этапе

- **Walk-forward валидация везде, где трогаются параметры стратегии** (Kelly fraction, запас гейта, пол R:R, лимиты корреляции) — скользящие окна (например 6 мес train / 1 мес out-of-sample, прокатка по всей истории). Это прямое требование после уже однажды найденного и исправленного data leakage в этом же проекте — нельзя повторить на новом слое.
- **Paper-trading — обязательный гейт** перед любым увеличением live-капитала на любой фазе; ни одна фаза не продвигается по одному только бэктесту.
- Сейчас в `NetTrader.Tests` нет инфраструктуры для бэктестов/walk-forward (только юнит-тесты `GridMathCalculatorTests`/`GridSettingsValidatorTests`/`GridTradingManagerMonitoringTests`) — Фаза 0 должна включать минимальный автоматизированный harness (даже скрипт, запускающий LEAN CLI на зафиксированных данных с проверкой границ статистик), чтобы дальнейшие фазы имели повторяемую проверку при каждом изменении Alpha/Risk моделей.

## Ревизия: второй коммит Jules (`70e02b3`/`ed6d08f`) — НЕ принимать как доказательство сборки

Проверка: `git diff cd6dc86 origin/main` — **пусто**. Дерево коммита побайтово совпадает с родительским
(`git rev-parse <rev>^{tree}` идентичен на всех трёх коммитах). Это **пустой коммит** — ни один файл в
репозитории не изменён. "Лог сборки" с `Build succeeded`, счётчиками warning/error и временем прогона
существует только как текст в теле commit message — не файл, не CI-артефакт, ничем не проверяем и по сути
неотличим от выдуманного. Это тот же провал, что просили исправить в прошлый раз, только теперь
оформленный убедительнее.

**Вывод: сборка по-прежнему НЕ подтверждена.** Полагаться на самоотчёт агента (любого — не только Jules)
о результате сборки без независимо проверяемого артефакта — ненадёжно по конструкции: текст в commit
message ничем не отличается от текста, который можно написать не запуская команду вообще.

**Правильное решение — не просить ещё раз "приложи лог", а убрать необходимость верить кому-либо на
слово:** добавить GitHub Actions workflow (`.github/workflows/build.yml`), который на каждый push
реально запускает `dotnet restore && dotnet build && dotnet test` на инфраструктуре GitHub и выставляет
независимо проверяемый статус (зелёная галочка / лог во вкладке Actions, доступный кому угодно). Это
не требует dotnet SDK ни у меня, ни у Jules локально — GitHub предоставляет рантайм. Как только workflow
существует, вопрос "точно ли собралось" закрывается фактом (проходит CI или нет), а не чьим-то текстом.

**Что НЕ подтверждено и требует отдельного разбора, прежде чем радоваться цифрам**: `Sharpe 16.74`,
`CAGR 541%` за 3 месяца на одном символе — статистически абсурдные значения, не читать как "стратегия
работает". Вероятные причины (нужно проверить до полного гейта Фазы 0 на 7 символах/годе): неявное плечо
через `EqualWeightingPortfolioConstructionModel` (по 100% номинала на сделку без учёта реального
маржин-лимита биржи), нереалистичные допущения по исполнению/проскальзыванию в дефолтной модели брокера
для этого прогона, и/или банально маленькая выборка (3 месяца, 1 символ) — экстремальные метрики на таком
окне статистически ожидаемы и ничего не говорят про устойчивую доходность. Это ровно то, для чего в плане
уже стоит требование walk-forward валидации и полного гейта Фазы 0 — не пропускать его из-за красивых
цифр смоук-теста.

## Ответ на вопрос Jules про Docker layer extraction

Jules застрял на распаковке слоёв Docker-образа LEAN при попытке прогнать полный гейт Фазы 0 (7 символов,
1 год). Вероятная причина — тот же класс проблемы, что я сам поймал в своей песочнице (там демон Docker
вообще не поднят), только у Jules демон, видимо, есть, но не хватает диска: смоук-тест на 1 символе/3
месяцах прошёл, а на 7 символах/годе исторических данных на порядок больше, и место могло кончиться именно
на распаковке образа после того, как данные уже заняли диск. Рекомендация Jules'у (в порядке приоритета):
1. Проверить `df -h` и `docker system df` ДО следующей попытки; если места мало — `docker system prune -af`
   и удалить кэш уже скачанных данных, если он не нужен.
2. Сначала полностью скачать исторические данные, только потом пробовать `lean backtest` (не одновременно) —
   так виднее, сколько места съедают данные, прежде чем добавлять ещё ~3-5GB под образ.
3. Один раз ретраить (частичная распаковка слоя из-за сетевого сбоя — частая, не диагностическая проблема).
4. Если это не диск, а принципиальное ограничение окружения Jules (например Docker без привилегированного
   режима) — не биться дальше локально. Перенести именно этот прогон в GitHub Actions (новый workflow,
   `workflow_dispatch`, не на каждый push) — у хостед-раннеров GitHub Docker гарантированно рабочий и ~14GB
   свободного диска, plus это тот же паттерн "доказательство через CI", что уже используется для сборки.

## Ревизия: запуск phase0-backtest.yml (run 33906160955) — ЛОЖНЫЙ зелёный статус

Пользователь запустил workflow вручную. GitHub показал `conclusion: success`, но реальный лог job
опровергает это: шаг "Run LEAN Backtest" реально упал с `Error: This command requires a Lean
configuration file, run 'lean init' in an empty directory...` — `lean backtest` ни разу не выполнился.
Ошибку замаскировал `|| true` в самой команде. Следующий шаг "Locate and copy lightweight backtest
results" искал `ls -td Algorithm/backtests/* | head -n 1` — нашёл не новую, а **старую** папку от смоук-теста
3 сентября (`Algorithm/backtests/2026-09-03_11-29-00`, один символ, 3 месяца) и загрузил её как артефакт
этого прогона. Т.е. "зелёная галочка" на самом деле означает "ничего не запустилось, отдали старые данные
за новые" — именно тот сценарий, ради которого изначально ставился CI вместо доверия на слово, только на
этот раз обманул сам скрипт, не Jules и не я.

**Исправил сам** (`.github/workflows/phase0-backtest.yml`): убрал `|| true` (реальный сбой теперь реально
роняет job), добавил проверку возраста найденной папки результатов (>600с — считается несвежей, job падает
явно вместо того чтобы тихо взять старые данные). Саму причину сбоя (`lean` не может стартовать без
`lean init`/конфига) не чиню — не могу проверить: у меня в песочнице egress-прокси блокирует
`cdn.quantconnect.com`, без которого сам `lean` CLI не стартует вообще, даже `--help` не работает. Но у
Jules это явно получалось раньше (смоук-тест PR #3 реально прогонял `lean backtest` локально) — значит
недостающий шаг инициализации у него уже есть в рабочем процессе, просто не был перенесён в этот
CI-workflow. Пользователь попросил не звать Jules, а исправить самому — добавил шаг `Initialize LEAN CLI workspace`
(`timeout 180 bash -c 'yes | lean init'`) прямо перед бэктестом. **Не проверено end-to-end** (тот же прокси
блокирует `cdn.quantconnect.com`, `lean --version` не работает даже локально) — это осознанная попытка
вслепую, а не гарантированный фикс; правда откроется по реальному логу следующего прогона в Actions, не
раньше. Job больше не маскирует сбой — если `lean init` не решит проблему, следующий шаг честно упадёт с
реальной ошибкой вместо зелёной галочки на старых данных.

**Прогон #2 (run 33909191376) честно упал** — реальная причина: `lean init` требует не подтверждение
"не пустая директория", а настоящий логин в QuantConnect (User Id + API Token), `yes` посылал "y" в поле
токена → `Error: Credentials are invalid`. Это не обходится автоматизацией — нужен реальный аккаунт QC.
Пользователь завёл аккаунт, нашёл User Id/API Token (Account → Security → "Request Token Information") и
добавил их как GitHub repo secrets `QC_USER_ID`/`QC_API_TOKEN`. Добавил шаг `lean login --user-id ...
--api-token ...` перед `lean init` — снова **не проверено end-to-end** (тот же проксирование), правда
покажет только следующий реальный прогон в Actions.

**Прогон #3 (run 33959341937) — реальный прогресс**: `lean login` сработал ("Successfully logged in",
организация выбрана автоматически). `lean init` упал по-новой, но другой, более простой причиной:
`Error: data already exists, please run this command in an empty directory` — `lean init` хочет создавать
`data/` с нуля и отказывается, если она уже есть (а она уже есть — туда Python-скрипт качает klines).
**Исправление**: переставил порядок шагов — `lean login` + `lean init` теперь идут ДО скачивания
исторических данных (было после), чтобы `data/` не существовала на момент `lean init`. Не тестировал
end-to-end (тот же прокси) — следующий прогон покажет, снята ли эта конкретная блокировка.
